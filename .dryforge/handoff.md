# handoff — Grok 메일 "분류 링크" 양식 전환과 게시물 정보 자동 조회

## 문서 역할과 충돌 해결

| 문서 | 역할 |
|---|---|
| `.dryforge/spec.md` | **무엇을 만드는가**: 동작과 데이터 계약. 기준 문서다. 충돌하면 spec이 이긴다. spec을 고치려면 사용자 승인이 필요하다 |
| `.dryforge/plan.md` | **어떤 순서로, 어디에**: 작업, 대상 파일, 실행 순서. 잠정적인 설계도이므로 자유롭게 고쳐도 된다 |
| `.dryforge/handoff.md` | 이 문서. 실행 규칙, 넘을 수 없는 조건, 문서에 담기지 않은 의도, 그리고 아래의 프로젝트 기반(실행 대상 아님) |

소재함 첫 버전은 이미 구현되어 운영 중이다(`main`, 최근 커밋 `780cf64`). 이번 작업은 그 위에서 메일 양식과 카드
내용을 바꾸는 변경이다. 원격 저장소는 `origin` = https://github.com/ardenspace/material-page.git 이고, Supabase
프로젝트는 CLI에 연결되어 있다(`supabase/.temp/project-ref`). 이전 설계 문서는 git 기록(`3a6c4a9`)에 남아 있다.

## 실행 모양

작업 6개를 3단계로 진행한다.
- 1단계: `{T1 DB, T2 해석기, T4 화면, T5 안내서}`
- 2단계: `{T3 조회와 입구 API}` (T2의 카드 형식을 쓴다)
- 3단계: `{T6 배포}` (사용자 확인 필요)

## 넘을 수 없는 조건

1. **원문으로 갈 링크가 없는 것은 카드로 만들지 않는다.** 링크가 없는 메일, 잘려서 버린 링크는 카드도 메일 본문도
   저장하지 않는다. 회차 행(메일 ID, 받은 시각)만 남긴다. 해석기가 `raw` 카드를 만드는 경로를 되살리지 않는다.
2. **잘린 메일(`Continue reading` 포함)의 마지막 링크는 항상 버린다.** 번호 중간에서 잘린 링크가 다른 게시물을
   가리키거나 이미 본 게시물로 영구 기록되는 것을 막기 위해서다. "번호가 온전해 보이면 살린다"로 바꾸지 않는다.
3. **조회 실패가 메일 처리를 실패시키면 안 된다.** 외부 조회의 어떤 오류도 입구 API 응답을 500으로 만들지 않는다.
   500은 DB 저장 실패일 때만이다.
4. **입구 API 응답 형식은 바꾸지 않는다.** Gmail 스크립트가 `status`, `batchId`, `parsed`, `raw`, `skipped`를 검사한다.
5. **기존 데이터와 칸은 그대로 둔다.** 새 마이그레이션은 칸 추가와 `ingest_batch` 본문 교체만 한다. 예전 카드 화면
   모양도 유지한다. `ingest_batch`의 이름·매개변수·권한·멱등·원자성은 바뀌지 않는다.
6. **사진은 pbs.twimg.com 주소만 저장하고 그대로 표시한다.** 다른 주소는 버린다(DB 제약으로도 막는다).
7. **게시물 본문은 글자로만 표시한다.** HTML로 해석하지 않는다.
8. **완전 무료.** 유료 API나 유료 요금제를 쓰지 않는다. 게시물 조회는 공개 주소(syndication, oEmbed)로만 한다.
9. **원격 반영은 사용자 확인 뒤에만.** `supabase db push`, `supabase functions deploy ingest --no-verify-jwt`,
   `git push origin main`은 각각 실행 직전에 확인을 받는다. 순서는 DB → 함수 → push이고, 한국 시간 오전·오후 8~9시
   (수집 시각)를 피한다.
10. **검증 명령 `pnpm verify`**(린트, 타입 검사, 단위·API 테스트, DB 테스트, 빌드)가 각 작업이 끝날 때와 병합 뒤에
    통과해야 한다. DB 테스트는 로컬 Supabase(`supabase start`, Docker 필요)를 대상으로 한다.
11. 이 프로젝트의 Next.js는 학습 자료와 다를 수 있다. 화면 코드를 고치기 전에 `node_modules/next/dist/docs/`의 관련
    안내를 확인한다(`AGENTS.md`). 보드 사이트는 서버 없는 정적 사이트로 유지한다.
12. 사용자 화면의 모든 문구는 한국어, 시각은 한국 시간(KST)이다.

## 사람이 해야 하는 일

- 배포가 끝나면 Grok 예약 요청의 양식 문장을 spec 3장의 문장으로 바로 교체한다(사용자가 직접 할 유일한 일).
- 오늘 이미 들어온 양식 오류 카드를 휴지통으로 옮긴다(사용자가 직접 하기로 함).
- 배포 뒤 실제 메일 1통으로 카드 수, 표시, 원본 링크 이동, 검색을 확인한다.

## 문서에 담기지 않은 의도와 위험

- **이번 변경의 이유**: Grok 메일은 약 475자에서 잘린다. 항목을 "분류 링크" 한 줄로 줄여서 한 메일에 들어오는 소재
  수를 늘리고, 요약 대신 실제 게시물 내용을 조회해서 보여 준다. Grok의 요약·재밌는 이유는 새 카드에서 사라지는 것이
  의도된 결과다.
- **링크 없는 메일을 카드로 남기지 않는 이유**: 사용자는 원문으로 갈 수단이 없는 카드는 쓸모가 없다고 판단했다.
  링크만 주는 것이 이번 설계이므로, 링크가 없는 메일은 정상 결과가 아니다.
- **잘린 본문과 원본 링크**: 카드의 원본 링크는 메일의 게시물 주소로 만들기 때문에, 카드 본문이 어떻든 항상 원문으로
  이동한다. 본문 끝의 t.co 주소는 사진·인용을 가리킬 뿐이라 지우고, 긴 글은 전문이 있으면 전문을 저장하기로 했다.
- **syndication 주소는 비공식이다.** `token=a`로 동작하는 것을 2026-09-27에 확인했지만 언제든 막힐 수 있다. 막히면
  oEmbed로 넘어가고, 둘 다 막히면 링크만 있는 카드가 된다. 이 경우를 오류로 취급해 메일을 실패시키지 않는다.
- **oEmbed 카드에는 작성 시각이 없다.** oEmbed는 날짜만 주므로 시각 칸을 비우고 표시하지 않는다. 날짜만 채워 넣어서
  정밀도가 섞이게 하지 않는다.
- **예전 카드와 새 카드의 구분**은 `summary`가 null인지로 한다(spec 7.1). 구분용 칸을 새로 만들지 않는다. 사용자가
  추가할 칸을 명시했기 때문이다.
- **배포 사이 구간**: DB 적용과 Grok 요청 교체 사이에 메일이 들어오면 카드가 '조회 실패'나 '기타'로 보일 수 있다.
  사용자는 수집 시각을 피해 연달아 배포하고, 그래도 생긴 카드는 그대로 두기로 했다.
- **버린 대안**
  - 19자리 번호만 인정: 오래된 게시물까지 버려져서 쓰지 않는다.
  - 잘린 링크도 그대로 저장: 다른 게시물을 가리키고 영구 기록되어서 쓰지 않는다.
  - 링크 앞 글자를 그대로 비교: Grok이 번호나 글머리표를 붙이면 모두 '기타'가 되어서, 번호·기호를 떼고 비교한다.
  - Grok API 직접 호출: 무료로 쓰기 위해 메일을 거친다는 기존 결정을 유지한다.

- **무엇**: 강원도 공감형 콘텐츠(캐릭터와 함께 만드는 콘텐츠)를 만드는 팀의 내부용 소재 공유 보드 "소재함"이다.
  Grok이 X에서 찾은 강원도 관련 밈, 웃긴 게시물, 화제, 반응을 메일로 받고, 팀이 그 소재를 같이 보고 저장·삭제하며
  의견과 별점을 남긴다.
- **누구**: 소규모 팀(몇 명). 관리자는 1명(ardensdevspace@gmail.com)이다.
- **규모**: 하루 두 번 회차가 들어오고, 회차마다 소재가 수~수십 개다. 동시 사용자는 한 자릿수다.
- **제약**: 완전 무료 운영, 소재는 무료 Grok의 예약 메일로 받음(본문 약 475자에서 잘림), 폰과 PC에서 사용, 상업 용도가
  허용되는 호스팅.
- **깊이 방향**: 내부 소규모 협업 도구다. 도메인 규칙(상태, 중복, 권한)은 정확하게 지키고, 인프라는 무료 관리형
  서비스에 맡겨 가볍게 간다.

### 2. 도메인 모델

**개념**
- **팀원·관리자**: 구글 계정(이메일 소문자 비교)으로 식별하고, 허용 목록에 있어야 입장한다. 관리자만 목록을 관리하며
  관리자 자신은 빠질 수 없다. 제거되면 즉시 접근이 끊기지만 댓글·별점·이름은 남는다.
- **회차**: Grok 메일 1통 = 회차 1개. 받은 시각(KST)이 제목이다. 같은 메일은 한 번만 들어온다. 회차는 사라지지 않고,
  카드가 없는 회차는 화면에만 안 보인다. 링크가 없는 메일도 회차 행은 생긴다.
- **소재(카드)**: X 게시물 1개. 분류, 원본 링크, 그리고 입구에서 조회한 작성자 이름·아이디, 작성 시각, 본문, 첫 사진,
  좋아요·댓글 수를 담는다. 조회에 실패하면 분류와 링크만 담는다. 예전 카드(요약·재밌는 이유·리트윗을 담은 카드,
  해석하지 못한 원문을 담은 '양식 오류' 카드)는 그대로 남아 있지만 새로 만들지 않는다.
  - 상태: 모음 → 저장됨 ↔ 모음, 모음/저장됨 → 휴지통 → 원래 자리로 복구, 또는 보존 기간(기본 30일) 뒤 영구 삭제
  - 내용은 고칠 수 없다.
- **이미 본 게시물**: X 게시물 번호의 영구 기록이다. 한 번 들어온 게시물은 다시 들어오지 않는다. 조회에 실패한
  게시물도 기록된다. 잘려서 버린 링크는 기록되지 않는다.
- **댓글**: 팀원 의견. 작성자 본인만 고치고 지운다(관리자도 남의 것은 불가). 휴지통 소재에는 달 수 없고, 소재가
  영구 삭제되면 같이 사라진다.
- **별점**: 팀원마다 소재 하나에 1~5점 하나. 바꾸고 취소할 수 있고, 누가 몇 점을 줬는지 팀 전체에 공개된다.
- **분류**: 밈 / 웃긴 게시물 / 화제 / 반응 / 기타. Grok은 "웃긴"으로 써도 되며 '웃긴 게시물'로 저장한다.

**개념 사이의 규칙**
- 저장, 저장 취소, 삭제, 복구는 사용자가 본 상태에서 DB 조건부 변경을 먼저 성공한 쪽이 이긴다.
- 댓글과 별점은 소재의 상태를 따라다니고, 휴지통에서는 얼어 있다.
- 영구 삭제되어도 이미 본 게시물 기록은 남는다.
- 원문으로 갈 링크가 없는 것은 카드가 되지 않는다.

**용어**: "소재 모음" = `inbox`, "저장됨" = `saved`, "휴지통" = `trashed`, "양식 오류" = 예전 `raw` 카드,
"회차" = 메일 1통, "조회 실패 카드" = 게시물 정보를 가져오지 못해 분류와 링크만 있는 카드

### 3. 기술 결정 (사용자 확정)

- **구조**
  - 화면: Next.js(TypeScript) 정적 내보내기, Cloudflare Pages 무료 정적 호스팅(저장소 연결, `main` push로 배포),
    사용자 도메인. 데이터 접근은 모두 브라우저의 Supabase 클라이언트로 한다.
  - 메일 입구: Supabase Edge Function `ingest`. 해석 → 게시물 정보 동시 조회(syndication → oEmbed → 링크만) →
    DB 함수 `ingest_batch` 한 번 호출 순서다.
  - 데이터, 구글 로그인, 실시간 반영: Supabase 무료 요금제
  - 메일 전달: 관리자 Gmail의 Apps Script가 KST 오전·오후 8:10~8:40쯤 제목이 `강원도 밈`으로 시작하는 메일을 골라
    입구로 보낸다. 최초 3일 조회 뒤로는 저장된 완료 지점부터 재개한다.
  - 실시간: 현재 팀원에게만 허용되는 변경 신호 행의 UPDATE를 구독하고, 업무 데이터는 권한 확인 뒤 재조회한다.
- **보안**: 구글 로그인 + 관리자가 관리하는 허용 목록. 권한은 DB 행 단위 규칙으로 강제한다. 입구는 공유 비밀값으로
  보호하고, 소재 쓰기는 입구의 서비스 권한만 할 수 있다. 관리자는 허용 목록의 `admin` 행 하나로 정한다. 외부에서 받은
  게시물 내용은 글자로만 표시하고 사진은 pbs.twimg.com 주소만 허용한다.
- **동시성**: 상태 변경은 `expected_status` 조건부 변경이다. 댓글·별점·휴지통 이동은 부모 소재 잠금으로 직렬화한다.
  입구는 메일 ID로 멱등이고, 다른 메일의 같은 게시물 경합은 고유 제약으로 처리한다.
- **관례**: TypeScript, pnpm, 한국어 UI. 자동 테스트는 핵심 규칙(해석, 조회 변환, 중복, 권한, 상태)에 두고 화면은 사람이
  확인한다. 검증 명령은 `pnpm verify`다.
- **운영**: 무료 DB는 7일 활동이 없으면 잠들지만 하루 두 번 오는 메일이 활동이 된다. 휴지통 자동 삭제는 DB 예약
  작업이다. 실패한 메일 조회 구간은 완료 처리하지 않고 다음 실행에서 재시도한다.

### 4. 앞으로의 범위 (이번에 구현하지 않음)

- Grok 보낸 사람 주소를 알게 되면 메일 선별 조건에 추가
- 팀원이 직접 소재를 추가하는 기능
- 분석: 별점, 분류, 좋아요·댓글 수를 CSV나 분석 화면으로 보기
- 조회에 실패한 카드의 게시물 정보를 나중에 다시 조회하는 기능, 이미 본 게시물의 조회를 생략하는 최적화
- 알림
