# handoff — 소재함 첫 버전

## 문서 역할과 충돌 해결

| 문서 | 역할 |
|---|---|
| `.dryforge/spec.md` | **무엇을 만드는가**: 동작과 데이터 계약. 기준 문서다. 충돌하면 spec이 이긴다. spec을 고치려면 사용자 승인이 필요하다 |
| `.dryforge/plan.md` | **어떤 순서로, 어디에**: 작업, 대상 파일, 실행 순서. 잠정적인 설계도이므로 자유롭게 고쳐도 된다 |
| `.dryforge/handoff.md` | 이 문서. 실행 규칙, 넘을 수 없는 조건, 문서에 담기지 않은 의도, 그리고 아래의 프로젝트 기반(실행 대상 아님) |

지금은 빈 프로젝트다(초기 커밋만 있다). 원격 저장소는 `origin` = https://github.com/ardenspace/material-page.git 이고,
사용자가 여기에 커밋하라고 했다.

## 실행 모양

준비 작업(스캐폴드) 뒤에 작업 7개를 3단계로 나눠 진행한다.
- 1단계: `{T1 DB, T2 해석기, T7 Gmail 스크립트·안내서}`
- 2단계: `{T3 입구 API, T4 로그인·팀원 관리, T5 댓글·별점 조각}`
- 3단계: `{T6 페이지·카드}`

T1 뒤에는 DB 타입을 다시 만든다(plan의 `regen_barriers`).

## 넘을 수 없는 조건

1. **완전 무료.** 유료 요금제나 카드 등록이 필요한 기능은 쓰지 않는다. Supabase 무료, Cloudflare 무료, 구글 스크립트
   무료만 쓴다. 유료 AI 호출도 쓰지 않는다. 해석은 규칙 기반이다.
2. **권한은 DB에서 강제한다.** 다음은 행 단위 규칙이나 DB 함수로 막는다. 화면에서 숨기는 것만으로는 부족하다.
   - 팀원이 아닌 사람과 제거된 팀원의 접근
   - 남의 댓글 수정·삭제(관리자도 불가)
   - 관리자가 아닌 사람의 팀원 관리, 관리자 자기 자신 제거
   - 휴지통 소재에 댓글·별점 달기
3. **이미 본 게시물 기록은 영구히 남긴다.** 완전 삭제될 때도 지우지 않는다. 지운 소재가 다시 나타나지 않게 하는 것이
   사용자의 의도다.
4. **입구 API는 멱등이고 원자적이다.** 같은 `messageId`로는 회차가 하나만 생기고, 한 메일의 쓰기는 전부 되거나 전부
   안 된다.
5. **상태 변경은 사용자가 본 `expected_status`와 같을 때만 원자적으로 적용한다.** DB에서 조건부 변경을 먼저
   성공한 쪽이 이기고 늦은 쪽은 안내를 받는다. 삭제도 `inbox`/`saved` 중 요청이 본 상태 하나와 비교한다.
   댓글·별점 쓰기, 휴지통 이동, 복구·자동 삭제는 같은 소재에서 잠금으로 직렬화하고 현재 상태를 재확인한다.
6. **손으로 붙여넣는 화면은 만들지 않는다.** 사용자가 명시적으로 자동 전달만 하기로 했다. 카드 내용을 고치는 기능도
   없다.
7. **검증 명령 `pnpm verify`**(린트, 타입 검사, 단위·API 테스트, DB 테스트, 빌드)가 각 작업이 끝날 때와 병합 뒤에
   통과해야 한다. DB 테스트와 API 테스트는 로컬 Supabase(`supabase start`, Docker 필요)를 대상으로 돈다. 이 기기에는
   Docker, Supabase CLI, Node 24, pnpm이 있는 것을 확인했다.
8. 비밀값(서비스 권한 키, `INGEST_SECRET`)은 코드나 저장소에 넣지 않는다. `.env.example`에는 이름만 적는다.
9. 사용자 화면의 모든 문구는 한국어로 쓰고, 시각은 한국 시간(KST)으로 표시한다.
10. **보드 사이트는 서버 없는 정적 사이트다.** 서버에서 그리는 화면, 서버 라우트, 미들웨어를 쓰지 않는다. 서버 쪽
    로직이 필요하면 DB 함수나 Supabase 서버 기능에 둔다. 이유: Cloudflare 무료 요금제의 서버 코드 크기 제한
    (압축 약 3MB)을 넘으면 유료가 필요하다. 사용자가 "처음부터 가볍게"를 골랐다.
11. **관리자 정보는 DB 한 곳에만 둔다.** 마이그레이션이 허용 목록에 관리자 행을 넣고, 환경 변수로는 따로 두지 않는다.
12. **메일 재시도는 완료 지점을 보존한다.** 최초 3일 조회 이후에는 저장된 완료 지점부터 재개한다. 모든 대상의
    성공 응답 확인 전에는 구간을 완료 처리하지 않는다. 3일 넘는 장애나 실행 중단으로 미처리 메일을 버리지 않는다.
13. **실시간 변경은 공통 데이터 계층에서 재조회한다.** 업무 테이블을 직접 구독하지 않고, 현재 팀원만 읽는
    변경 신호 행의 UPDATE를 구독한다. 삭제도 신호로 알리고 본문·업무 행 ID를 전송하지 않는다.
    댓글 검색 결과·별점순 정렬·빈 회차·자동 삭제와 재접속 동기화를 함께 처리한다.
14. **제거된 팀원의 기존 JWT·구독도 검증한다.** 제거 커밋 뒤 시작하는 요청은 현재 DB 허용 목록으로 차단한다.
    화면은 요청·갱신·재접속·탭 복귀 및 활성 탭의 30초 주기 확인에서 제거를 감지하면 캐시를 비우고 접근을 막는다.
    이미 전달된 정보의 회수나 잠든 브라우저의 즉시 화면 정리를 보장한다는 뜻은 아니다(spec 3장).

## 사람이 해야 하는 일 (실행기가 대신할 수 없음)

실행기는 코드, 안내서(`docs/setup.md`), 로컬 검증까지만 한다. 다음은 사용자가 안내서를 보고 직접 한다.
- Supabase 프로젝트 생성, 구글 클라우드 OAuth 클라이언트 설정
- Cloudflare 배포와 도메인 연결
- Gmail 스크립트 설치와 권한 승인
- Grok 요청의 양식 문장 유지 및 적용 후 결과 확인(사용자가 2026-09-26 오전에 적용함)

실제 메일 1통이 보드에 뜨는지 확인하는 것도 배포 후에 사람이 한다.
양식 적용 후 메일을 별도로 확인하고, 두 계정으로 실시간 검색·정렬과 팀원 제거 화면 처리를 검증한다.
Gmail 스크립트의 장기 중단·실패·중복 재전송 복구도 테스트용 설정으로 수동 확인한다(spec 11장, plan T7).

## 문서에 담기지 않은 의도와 위험

- **메일을 거치는 이유**는 Grok을 무료로 쓰기 위해서다. "Grok API를 직접 부르면 더 간단하다"는 방향으로 바꾸지 않는다.
- **실제 메일 확인(2026-09-26)**: 사용자가 Grok 예약 요청으로 받은 메일의 제목과 본문 일부를 제공했다.
  제목은 `강원도 밈 업데이트!`이고, 본문에는 `gangwon-auto is ready`, 제목, 소개글과 실제 게시물 링크·요약이
  들어 있다. 이 예시는 양식 문장 적용 전 결과다. 사용자는 같은 날 오전에 양식 문장을 적용했으며, 적용 후 결과는
  아직 이 검토에서 확인하지 않았다. 기존 예시만으로 해석 양식을 바꾸지 않는다.
- **메일 선별은 제목 기준**: 사용자 결정에 따라 제목의 앞뒤 공백 제거 후 `강원도 밈 업데이트!`와 정확히 일치하는
  메시지를 전달한다. 본문의 시작 표시가 없어도 전달하여 원문 카드로 보존한다. 발신자 주소는 아직 확인하지
  않았으며, 나중에 주소를 알게 되면 스크립트 설정에 추가하는 것은 다음 작업으로 미룬다.
- **확인할 위험**: 실제 Grok 메일에 사용자가 쓴 요청문(양식 예시 포함)이 함께 인용되어 오면, 예시 블록
  (`링크: https://x.com/.../status/...`)이 유효하지 않은 링크 때문에 `raw` 카드로 올라올 수 있다. 양식 적용 후 메일에서
  블록 표시와 실제 항목이 유지되는지, 요청문 예시까지 인용되는지 확인한다. 해석 규칙을 임의로 바꾸지 않는다.
- **별점을 전원 공개하는 것은 사용자가 고른 것이다.** 카드에 누가 몇 점을 줬는지 모두 보인다. 익명으로 "개선"하지 않는다.
- **검토 보완(2026-09-26)**: 재시도 완료 지점, 공통 실시간 재조회, 기존 연결의 권한 차단, 동시성·롤백 검증을
  사용자 요청으로 문서에 반영했다. 구현을 수행한 것은 아니다. 서버 권한·경합·실제 구독 검증은 핵심 자동 테스트에
  포함하고, 화면과 Gmail 스크립트는 수동 검증 범위를 유지한다.
- **버린 대안**
  - 구글 시트 + 구글 스크립트만으로 만드는 방식: 화면 제약이 크고, 개인 계정끼리는 접속자를 구분하기 어렵다.
  - Firebase: 서버 기능을 쓰려면 카드 등록이 필요하다.
  - Vercel 무료: 약관상 비상업 용도로 제한된다. 사용자는 Cloudflare와 자기 도메인을 골랐다.
  - 다른 AI로 메일 해석: 비용이 들고 가끔 틀린다.
  - 보드 서버가 Gmail을 직접 읽는 방식: OAuth 토큰 관리와 무료 호스팅의 예약 실행 제한 때문에 쓰지 않는다.
  - 서버 기능을 쓰는 Next.js를 Cloudflare Workers(OpenNext)에 올리는 방식: 무료 요금제의 크기 제한을 넘을 위험이
    있어서 쓰지 않는다. 기능 차이는 없다.

## 프로젝트 기반 (Project Foundation)

> **실행 대상이 아닌 프로젝트 맥락이다.** `go`는 이 절을 맥락과 하네스의 원천으로 읽을 뿐, 구현 대상으로 삼지 않는다.
> 구현 대상은 `spec.md`다.

### 1. 프로젝트 정체성

- **무엇**
  - 강원도 공감형 콘텐츠(캐릭터와 함께 만드는 콘텐츠)를 만드는 팀의 내부용 소재 공유 보드 "소재함"이다.
  - Grok이 X에서 찾은 강원도 관련 밈, 웃긴 게시물, 화제, 반응을 메일로 받는다. 팀이 그 소재를 같이 보고 저장·삭제하고
    의견과 별점을 남긴다.
- **누구**: 소규모 팀(몇 명)이다. 관리자는 1명(ardensdevspace@gmail.com)이다.
- **규모**: 하루 두 번 들어오는 회차마다 소재가 수~수십 개다. 동시 사용자는 한 자릿수다.
- **제약**
  - 완전 무료로 운영한다.
  - 소재는 무료 Grok의 메일을 통해 받는다.
  - 폰과 PC에서 모두 쓴다.
  - 채널이 수익을 낼 수 있으므로 상업 용도가 허용되는 호스팅을 쓴다.
- **깊이 방향**: 내부 소규모 협업 도구다. 도메인 규칙(상태, 중복, 권한)은 정확하게 지키고, 인프라는 무료 관리형
  서비스에 맡겨 가볍게 간다.

### 2. 도메인 모델

**개념**
- **팀원·관리자**
  - 구글 계정으로 식별한다(이메일은 소문자로 비교). 허용 목록에 있어야 입장할 수 있다.
  - 관리자만 목록을 관리하고, 관리자 자신은 목록에서 빠질 수 없다.
  - 제거되면 즉시 접근이 끊기지만, 그 사람이 남긴 흔적(댓글, 별점, 이름)은 남는다.
- **회차**
  - Grok 메일 1통이 회차 1개다. 받은 시각(KST)이 회차 제목이 된다.
  - 같은 메일은 한 번만 들어온다.
  - 회차는 사라지지 않는다. 소재가 전부 빠진 회차는 화면에만 안 보인다.
- **소재**
  - X 게시물 1개에 대한 요약, 재밌는 이유, 분류, 반응 수를 담는다. 또는 해석하지 못한 원문(양식 오류)을 담는다.
  - 상태: 모음 → 저장됨 ↔ 모음, 모음/저장됨 → 휴지통 → 원래 자리로 복구, 또는 30일 뒤 영구 삭제
  - 내용은 고칠 수 없다.
- **이미 본 게시물**: X 게시물 번호의 영구 기록이다. 한 번 들어온 게시물은 다시 들어오지 않는다.
- **댓글**
  - 소재에 대한 팀원 의견이다. 작성자 본인만 고치고 지울 수 있다(관리자도 남의 것은 불가).
  - 휴지통 소재에는 달 수 없고, 소재가 영구 삭제되면 같이 사라진다.
- **별점**
  - 팀원마다 소재 하나에 1~5점 하나를 준다. 바꾸고 취소할 수 있다.
  - 누가 몇 점을 줬는지 팀 전체에 공개된다.
  - 나중에 반응 좋은 소재를 분석하는 재료다.
- **분류**: 밈 / 웃긴 게시물 / 화제 / 반응. 그 밖의 값은 기타다.

**개념 사이의 규칙**
- 저장, 저장 취소, 삭제, 복구는 같은 출발 상태에서 DB 조건부 변경을 먼저 성공한 쪽이 이긴다.
- 댓글과 별점은 소재의 상태를 따라다니고, 휴지통에서는 얼어 있다.
- 영구 삭제되어도 이미 본 게시물 기록은 남는다.
- 전체 규칙은 `spec.md` 4, 5, 7, 8장에 있다.

**용어**
- "소재 모음" = `inbox`
- "저장됨" = `saved`
- "휴지통" = `trashed`
- "양식 오류" = `raw` 카드
- "회차" = 메일 1통

### 3. 기술 결정 (사용자 확정)

- **구조**
  - 화면은 Next.js(TypeScript)의 **정적 내보내기**로 만들고 Cloudflare 무료 정적 호스팅에 배포한다. 사용자의
    도메인을 연결한다. 데이터 접근은 모두 브라우저의 Supabase 클라이언트로 한다.
  - 메일 받는 입구는 Supabase 서버 기능(Edge Function, 무료) `ingest`다.
  - 데이터, 구글 로그인, 실시간 반영은 Supabase 무료 요금제를 쓴다.
  - 메일은 관리자 Gmail에서 도는 구글 스크립트가 KST 오전·오후 한 번씩(8:10~8:40, 20:10~20:40 예상)
    제목 `강원도 밈 업데이트!`의 정확한 일치로 골라서
    입구 API로 보낸다(제목 앞뒤 공백 제거, 메시지별 판정). 본문의 시작 표시는 선별 조건이 아니다.
    최초 조회만 최근 3일부터 시작하고 이후에는 저장된 완료 지점과 겹치는 구간부터 따라잡는다.
  - 실시간은 현재 팀원에게만 허용되는 변경 신호 행의 UPDATE를 구독한다. 업무 데이터는 권한 확인 후 DB에서
    재조회한다. 업무 테이블 자체는 Realtime publication에 넣지 않는다.
- **보안**
  - 입장은 구글 로그인과 관리자가 관리하는 이메일 허용 목록으로 판정한다.
  - 권한(팀원 여부, 댓글 본인만, 관리자만 팀원 관리)은 DB의 행 단위 규칙으로 강제한다.
  - 입구 서버 기능은 공유 비밀값으로 보호한다. 소재 쓰기는 그 기능의 서비스 권한만 할 수 있다.
  - 관리자는 DB 허용 목록의 `admin` 행 하나로 정한다.
  - 감사 기록은 별도로 두지 않는다. 댓글과 별점에 작성자와 시각이 남는 것으로 충분하다.
- **동시성**: 상태 변경은 `expected_status`에 대한 원자적 조건부 변경이다. 댓글·별점 쓰기와 휴지통 이동은
  부모 소재 잠금으로 직렬화한다. 입구는 메일 ID로 멱등이며 다른 메일의 동일 게시물 경합도 고유 제약으로 처리한다.
- **관례**
  - TypeScript, pnpm, 한국어 UI
  - 자동 테스트는 핵심 규칙(해석, 중복, 권한, 상태 규칙)에 둔다. 화면은 사람이 확인한다.
  - 검증 명령은 `pnpm verify`다.
- **운영**
  - 무료 DB는 7일간 활동이 없으면 잠든다. 매일 두 번 오는 메일이 활동이 된다.
  - 휴지통 자동 삭제는 DB 예약 작업으로 한다.
  - 실패·중단된 메일 조회 구간은 완료 처리하지 않는다. 오래된 미완료 구간도 재시도하며 원본이 Gmail에 남아
    있어야 복구할 수 있다. 반복 실패는 실행 로그와 안내서 절차로 해결한다.
