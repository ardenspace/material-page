# spec — Grok 메일 "분류 링크" 양식 전환과 게시물 정보 자동 조회

## 1. 목표와 동기

- Grok 예약 메일은 본문이 약 475자에서 잘리고 끝에 "Continue reading"이 붙는다. 기존 `===강원소재===` 양식은
  항목 하나가 길어서, 한 메일에 소재가 2~3개만 들어왔다.
- 그래서 Grok에게는 한 줄에 "분류 링크"만 쓰게 하고, 게시물 내용(작성자, 본문, 사진, 좋아요·댓글 수, 작성 시각)은
  입구 API가 X의 공개 조회 주소에서 직접 가져온다. 같은 475자 안에 훨씬 많은 소재가 들어오게 하는 것이 목표다.
- 원칙: 원문으로 갈 수 있는 링크가 없는 것은 카드로 만들지 않는다. 조회에 실패해도 링크가 있으면 카드는 남긴다.

## 2. 이번 범위

**바꾸는 것**
- Grok 요청 문장(안내서 `docs/setup.md` 6장)
- 메일 해석 규칙(`supabase/functions/_shared/parse.ts`)
- 입구 API에서 게시물 정보 조회 후 저장(`supabase/functions/ingest/`)
- DB: `materials` 칸 추가, `ingest_batch` 본문 변경(새 마이그레이션)
- 카드 화면과 검색(`src/components/Board.tsx`, `src/lib/model.ts`, 필요하면 `src/app/globals.css`)
- 관련 테스트

**바꾸지 않는 것**
- Gmail 스크립트(`gmail-script/Code.gs`)와 그 선별 규칙(제목이 `강원도 밈`으로 시작)
- 입구 API의 주소, 인증, 요청·응답 형식, 멱등성, 원자성
- 상태 규칙, 댓글·별점, 권한, 실시간 반영, 자동 삭제
- 기존 카드의 데이터와 화면 모양
- 오늘 이미 들어온 양식 오류 카드: 사용자가 직접 휴지통으로 옮긴다. 다시 수집하지 않는다.

## 3. Grok 요청 문장 (안내서 6장을 이 내용으로 교체)

기존 강원도 소재 검색 지시 끝에 붙이던 양식 문장을 아래로 바꾼다. 사용자는 배포가 끝난 뒤 Grok 예약 요청에서
직접 교체한다.

```
결과는 다른 말 없이, 한 줄에 게시물 하나씩 "분류 링크" 형식으로만 써줘.
분류는 밈 / 웃긴 / 화제 / 반응 중 하나로 쓰고, 링크는 x.com 게시물 주소 전체를 써줘.
소개글, 번호, 요약, 설명은 쓰지 마.
예) 밈 https://x.com/아이디/status/게시물번호
```

- 예시 줄의 링크는 숫자가 아닌 글자라서 해석기가 링크로 인식하지 않는다. 메일에 요청문이 인용되어 와도 카드가
  생기지 않는다.
- 안내서에는 교체 시점도 적는다: DB 적용, 함수 배포, 사이트 배포(이 spec 9장)가 끝나면 바로 교체한다. 교체 전에 오는 옛 양식 메일은 분류가
  '기타'로 들어올 수 있고, 그 카드는 그대로 둔다.

## 4. 메일 해석 규칙 (`parseMail`)

입력은 메일 본문 평문이다. 줄바꿈은 `\r\n`, `\r`을 `\n`으로 통일한 뒤 줄 단위로 처리한다.

1. **링크 찾기**: 본문 전체에서 X 게시물 링크를 나타난 순서대로 모두 찾는다. 한 줄에 여러 개가 있어도 모두 찾는다.
   - 유효한 링크: `http` 또는 `https`, 호스트가 `x.com`·`twitter.com` 또는 그 앞에 `www.`·`mobile.`이 붙은 형태,
     경로가 `/<계정>/status/<숫자>`. 계정은 영문·숫자·밑줄 1~15자다(지금 규칙과 같다).
   - `?` 뒤 쿼리, `#` 뒤 조각, 끝의 `/`, `/photo/1` 같은 추가 경로는 무시한다.
   - `post_id` = 숫자 부분, `url` = `https://x.com/<계정>/status/<숫자>`
   - 번호 바로 뒤에 숫자가 이어지지 않는 지점에서 번호가 끝난다(번호 전체를 취한다).
2. **분류**: 링크와 같은 줄에서 링크 앞에 있는 글자(그 줄의 앞선 링크가 있으면 그 링크 뒤부터)를 가져와 다음 순서로
   정리한 뒤 비교한다.
   - 앞뒤 공백 제거
   - 맨 앞의 번호 표시 제거: `1.`, `1)`, `(1)`, `[1]` 같은 숫자 표시와 그 뒤 공백
   - 맨 앞의 글머리표 제거: `-`, `*`, `•`, `·`와 그 뒤 공백
   - 맨 끝의 콜론(`:` 또는 `：`) 제거, 다시 앞뒤 공백 제거
   - 결과가 `밈`→`밈`, `웃긴` 또는 `웃긴 게시물`→`웃긴 게시물`, `화제`→`화제`, `반응`→`반응`. 그 밖의 글자나 빈 값은
     `기타`다. 비교는 정확히 일치해야 한다(포함 여부로 판정하지 않는다).
3. **잘린 메일**: 본문에 `Continue reading`(대소문자 무시)이 있으면, 그 문구보다 앞에서 찾은 링크 중 **마지막 하나를
   항상 버린다.** 번호가 온전해 보여도 버린다. 버린 링크는 카드도 이미 본 게시물 기록도 만들지 않으며 `skipped`에도
   세지 않는다. 문구 뒤에 링크가 더 있어도 해석 대상은 문구 앞의 링크뿐이다.
4. **메일 안 중복**: 같은 `post_id`가 다시 나오면 앞의 것만 남기고, 뒤의 것은 `skipped`에 센다.
5. **카드 순서**: 남은 링크에 나타난 순서대로 `position` 0, 1, 2, …를 매긴다.
6. **링크가 없는 메일**: 남은 링크가 없으면 카드를 만들지 않는다. 메일 본문은 어디에도 저장하지 않는다.
   해석기는 `raw` 카드를 더 이상 만들지 않는다.

해석 결과 카드 (조회 전):

```ts
{ kind: "parsed", position: number, post_id: string, url: string,
  category: "밈" | "웃긴 게시물" | "화제" | "반응" | "기타" }
```

## 5. 게시물 정보 조회 (입구 API, DB 저장 전)

- 해석이 끝나면 카드마다 게시물 정보를 **동시에** 조회한다. HTTP 요청 하나마다 제한 시간은 5초다(조정 가능).
- 조회 순서 (게시물마다):
  1. `GET https://cdn.syndication.twimg.com/tweet-result?id=<post_id>&token=a` (비공식 주소)
     - 성공 조건: 응답 200, JSON으로 읽힘, `__typename`이 `Tweet`이고 `user`가 있다. 그 밖(삭제·비공개 게시물의
       `TweetTombstone`, 빈 응답, 404, 시간 초과, 네트워크 오류)은 실패다.
  2. 1이 실패하면 `GET https://publish.x.com/oembed?url=<카드 url을 URL 인코딩>`
     - 성공 조건: 응답 200, JSON으로 읽힘, `author_name`이 있다.
  3. 둘 다 실패하면 링크만 저장한다(아래 칸이 모두 비어 있음).
- **조회 실패는 메일 처리를 실패시키지 않는다.** 어떤 조회 오류도 입구 API의 응답 코드를 바꾸지 않고, 링크만 있는
  카드로 이어진다.
- 이미 본 게시물인지와 관계없이 조회한다(중복 판정은 DB가 한다). 조회 횟수를 줄이는 최적화는 이번 범위가 아니다.

**syndication 응답 → 카드 칸**

| 칸 | 값 |
|---|---|
| `post_text` | 긴 글 전문 `note_tweet.note_tweet_results.result.text`가 있으면 그것. 없으면 `text`를 `display_text_range` [시작, 끝) 범위(유니코드 코드 포인트 기준)로 자른 것. 범위가 없거나 이상하면 `text` 그대로. 어느 경우든 `entities.media`에 있는 t.co 주소(`url` 값)가 남아 있으면 지우고 앞뒤 공백을 정리한다. HTML 엔티티(`&amp;`, `&lt;`, `&gt;`, `&quot;`, `&#39;`)는 글자로 바꾼다. 결과가 빈 문자열이면 비움(null) |
| `author_name` | `user.name` |
| `author_handle` | `user.screen_name` (앞에 `@`를 붙이지 않고 저장) |
| `likes` | `favorite_count` (0 이상 정수일 때만, 아니면 비움) |
| `replies` | `conversation_count` (0 이상 정수일 때만, 아니면 비움) |
| `posted_at` | `created_at` (해석 가능한 시각일 때 ISO 문자열, 아니면 비움). DB가 시각으로 변환하므로 다른 형식을 넘기지 않는다 |
| `image_url` | `mediaDetails`의 첫 항목의 `media_url_https`. 사진이면 사진, 동영상·GIF면 그 미리보기 사진이다. 주소가 `https://pbs.twimg.com/`으로 시작할 때만 저장하고, 아니면 비움 |

**oEmbed 응답 → 카드 칸**

| 칸 | 값 |
|---|---|
| `post_text` | `html` 안 첫 `<p …>…</p>`의 내용. `<br>`는 줄바꿈, 나머지 태그는 제거, HTML 엔티티는 글자로 바꾼다. 끝의 `pic.twitter.com/…`·`https://t.co/…` 주소는 지운다. 빈 문자열이면 비움 |
| `author_name` | `author_name` |
| `author_handle` | `author_url`의 마지막 경로 조각(예: `https://x.com/elonmusk` → `elonmusk`). 계정 규칙(영문·숫자·밑줄 1~15자)에 맞지 않으면 비움 |
| `likes`, `replies`, `image_url`, `posted_at` | 비움 (oEmbed는 날짜만 주므로 작성 시각은 저장하지 않는다) |

## 6. 데이터 계약

### 6.1 `materials`에 추가하는 칸 (새 마이그레이션, 모두 null 허용)

| 칸 | 형식 | 제약 |
|---|---|---|
| `post_text` | text | 없음 |
| `author_name` | text | 없음 |
| `author_handle` | text | 없음 |
| `image_url` | text | `image_url is null or image_url like 'https://pbs.twimg.com/%'` |
| `replies` | bigint | `replies >= 0` |
| `posted_at` | timestamptz | 없음 |

- 기존 칸, 기존 제약, 기존 데이터는 모두 그대로 둔다. `kind`의 `raw` 값과 `raw_text` 칸도 기존 카드 때문에 유지한다.
- 새로 들어오는 카드는 `kind = 'parsed'`이고 `retweets`, `summary`, `reason`, `raw_text`는 비어 있다(null).
  `likes`는 조회 결과를 넣는다.
- 권한: 새 칸도 기존 행 단위 규칙을 그대로 따른다(팀원만 읽기, 쓰기는 서비스 권한의 `ingest_batch`만).

### 6.2 `ingest_batch`

- 이름, 매개변수 `(p_message_id text, p_received_at timestamptz, p_items jsonb, p_skipped integer)`, 반환 형식,
  실행 권한(서비스 권한만), 잠금·멱등·원자성·중복 판정 동작은 그대로다. `create or replace`로 본문만 바꾼다.
- `p_items`의 각 항목:

```json
{ "kind": "parsed", "position": 0, "post_id": "1971234567890123456",
  "url": "https://x.com/abc/status/1971234567890123456", "category": "밈",
  "post_text": "…" , "author_name": "…", "author_handle": "abc",
  "image_url": "https://pbs.twimg.com/…", "likes": 12, "replies": 3,
  "posted_at": "2026-09-27T01:23:45.000Z" }
```

  `post_text`부터 `posted_at`까지는 값이 없으면 `null`이거나 빠져 있을 수 있다.
- 저장하는 칸: `batch_id, kind, post_id, url, category, post_text, author_name, author_handle, image_url, likes, replies,
  posted_at, position`. `retweets, summary, reason, raw_text`는 저장하지 않는다(null).
- 기존 `raw` 항목 처리 경로는 남겨 두어도 된다. 해석기가 더 이상 보내지 않는다.
- 항목이 0개인 메일도 회차 행(메일 ID, 받은 시각)은 만든다. 이 행이 같은 메일의 재전송을 `duplicate`로 막는다.
  카드가 없는 회차는 지금처럼 화면에 나타나지 않는다.

### 6.3 입구 API 응답 (변경 없음)

```json
{ "status": "created" | "duplicate", "batchId": "<회차 id>", "parsed": 0, "raw": 0, "skipped": 0 }
```

- 새 메일에서는 `raw`가 항상 0이다. `skipped` = 메일 안 중복 수 + 이미 본 게시물 수다. 잘려서 버린 링크는 세지 않는다.
- Gmail 스크립트가 이 형식을 검사하므로 키와 형식을 바꾸지 않는다.

## 7. 화면 (소재 모음, 저장됨, 휴지통의 카드)

### 7.1 카드 종류 판별

| 종류 | 조건 | 모양 |
|---|---|---|
| 예전 카드 | `kind = 'raw'`, 또는 `kind = 'parsed'`이고 `summary`가 null이 아님 | 지금 모양 그대로 |
| 새 카드 | `kind = 'parsed'`이고 `summary`가 null | 7.2 |
| 조회 실패 카드 | 새 카드 중 `post_text`와 `author_name`이 모두 null | 7.3 |

예전 해석기는 `parsed` 카드의 `summary`에 항상 문자열(빈 문자열 포함)을 넣었으므로 이 조건으로 구분된다.

### 7.2 새 카드 (위에서 아래 순서)

1. 분류 표시
2. 작성자 줄: `작성자 이름 @아이디 · 작성 시각`. 작성 시각은 기존 `kst()` 형식(한국 시간)이다. 값이 없는 부분은
   구분점과 함께 생략한다(예: 시각이 없으면 `이름 @아이디`).
3. 본문 `post_text` (줄바꿈 유지, 글자로만 표시하고 HTML로 해석하지 않음)
4. 첫 사진 `image_url`: 주소를 그대로 `<img>`로 표시한다(대체 문구 있음, 카드 폭에 맞춤, 지연 로딩). 없으면 생략한다.
   사진을 불러오지 못하면 사진 자리를 숨긴다.
5. `좋아요 N · 댓글 N` (천 단위 쉼표). 값이 없는 쪽은 생략하고, 둘 다 없으면 줄 전체를 생략한다.
6. `원본 보기 ↗` 링크(`url`, 새 탭, `noopener noreferrer`)

그 아래의 휴지통 정보, 저장·삭제·복구 버튼, 댓글·별점은 지금과 같다.

### 7.3 조회 실패 카드

- 분류 표시, 안내 문구 `게시물 정보를 불러오지 못했어요. 원본에서 확인해 주세요.`, `원본 보기 ↗` 링크만 보인다.
- 버튼, 휴지통 정보, 댓글·별점은 다른 카드와 같다.

### 7.4 검색

- 검색 대상에 `post_text`, `author_name`, `author_handle`을 추가한다. 기존 대상(요약, 재밌는 이유, 원문, 댓글)은 유지한다.
  대소문자 무시 포함 검색 방식은 지금과 같다.
- 검색창 안내 문구는 `본문, 작성자, 요약, 댓글 검색`이다.
- 분류 골라보기의 `양식 오류` 항목은 기존 카드 때문에 유지한다.

## 8. 예외 규칙 모음

| 상황 | 결과 |
|---|---|
| 링크가 없는 메일 | 카드 없음, 회차 행만 생성, `created`, 모든 수 0 |
| 잘린 메일에 링크가 하나뿐 | 그 링크를 버림 → 링크 없는 메일과 같음 |
| 링크 앞 글자가 `1. 밈`, `- 웃긴:` | 각각 `밈`, `웃긴 게시물` |
| 링크 앞 글자가 `재밌는 밈`, `링크:`, 없음 | `기타` |
| 같은 게시물이 `twitter.com`과 `x.com`으로 두 번 | 앞의 것만, `skipped` 1 |
| syndication 실패, oEmbed 성공 | 본문·작성자만 있는 새 카드(작성 시각·사진·수치 없음) |
| 둘 다 실패 | 조회 실패 카드 |
| 이미 본 게시물 | 카드 없음, `skipped` 증가(지금과 같음) |
| 같은 메일 재전송 | `duplicate`(지금과 같음) |
| `image_url`이 pbs.twimg.com이 아님 | 저장하지 않음 |

## 9. 배포와 사람이 할 일

- 순서: **DB 마이그레이션 적용(`supabase db push`) → 함수 배포(`supabase functions deploy ingest --no-verify-jwt`) →
  `git push`(Cloudflare Pages가 사이트를 다시 배포)**. 세 가지 모두 실행 직전에 사용자에게 확인을 받는다.
- 세 단계는 수집 시각(한국 시간 오전·오후 8~9시)을 피해서 연달아 진행한다. 끝나면 사용자에게 Grok 요청 문장을
  바로 교체하라고 안내한다. 그 사이에 들어온 카드가 '조회 실패'나 '기타'로 보여도 그대로 둔다.
- 사용자가 직접 하는 일은 배포 후 Grok 요청 문장 교체뿐이다. 실제 메일로 결과를 확인하는 것도 사용자가 한다.

## 10. 필수 검증

- `pnpm verify`(린트, 타입 검사, 단위·API 테스트, DB 테스트, 빌드)가 통과해야 한다. DB 테스트와 DB 동시성 테스트는
  로컬 Supabase(`supabase start`)를 대상으로 한다.
- 자동 테스트로 확인할 것
  - 해석기: 4장의 규칙 1~6과 8장의 해석 관련 행(링크 변형, 분류 정리, 잘린 메일, 링크 하나뿐인 잘린 메일, 메일 안
    중복, 링크 없음 → 빈 결과, 요청문 예시 줄은 링크로 인식하지 않음)
  - 조회: 외부 호출을 가짜 함수로 바꿔서 syndication 성공, syndication 실패 후 oEmbed 성공, 둘 다 실패, 시간 초과,
    tombstone, t.co 제거·긴 글 전문·코드 포인트 범위, pbs가 아닌 사진 주소 거부. 조회가 모두 실패해도 입구 API가
    200과 정상 결과를 돌려준다.
  - 입구 API: 인증·입력 검증(지금과 같음), 링크 없는 메일도 저장 함수를 한 번 호출하고 `created`를 전달
  - DB: 새 칸 저장, `retweets/summary/reason`이 null로 저장, `image_url`·`replies` 제약, 기존 멱등·중복·동시성 테스트
    유지(테스트 카드 모양은 새 계약으로 바꾼다)
- 사람이 확인할 것: 배포 후 실제 메일 1통에서 카드 수, 작성자·본문·사진·수치 표시, 원본 링크 이동, 검색
