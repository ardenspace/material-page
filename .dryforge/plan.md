# plan — 소재함 첫 버전

`spec.md`를 구현하는 작업 목록이다. 이 계획은 잠정적인 설계도이므로 필요하면 고쳐도 된다. 동작의 기준은 언제나
spec이다.

## 준비 작업 (작업 목록에 넣지 않음, 실행기가 먼저 수행)

- Next.js(App Router, TypeScript) 프로젝트를 **정적 내보내기(서버 없음) 설정**으로 만든다. 패키지 매니저는 pnpm이다.
  - 서버에서 그리는 화면, 서버 라우트, 미들웨어는 쓰지 않는다. 모든 데이터 접근은 브라우저의 Supabase
    클라이언트로 하고, 권한은 DB 규칙이 강제한다.
  - Cloudflare 무료 요금제의 서버 코드 크기 제한을 피하려고 사용자가 고른 방식이다.
- 브라우저용 Supabase 클라이언트 헬퍼의 뼈대를 만든다.
- `supabase init`으로 `supabase/` 폴더를 만든다. 마이그레이션, DB 테스트 폴더, 서버 기능 폴더
  (`supabase/functions/`, 공용 코드 `supabase/functions/_shared/`)를 포함한다.
  - `ingest` 기능은 로그인 토큰 검사를 끄도록 설정한다.
  - 공용 코드는 Deno(서버 기능)와 단위 테스트 도구에서 모두 불러올 수 있게, 외부 의존 없는 TypeScript로 쓴다.
- 테스트 도구(단위 테스트)와 린트를 설정한다.
- Cloudflare 무료 정적 호스팅 배포 설정을 둔다. 빌드 결과는 정적 파일 폴더다.
- `package.json` 스크립트를 만든다.
  - `lint`, `typecheck`, `test`(단위·API), `test:db`(`supabase test db`), `build`
  - `verify`: 위 스크립트를 모두 순서대로 실행한다.
- `.env.example`에 다음 이름을 적는다.
  - 사이트: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`
  - 서버 기능 비밀값(Supabase 쪽에 설정): `INGEST_SECRET`. 서비스 권한 키는 Supabase가 서버 기능에 자동으로 넣어 준다.
- 공통 레이아웃 파일(상단 제목 "소재함", 페이지 이동 자리)을 빈 틀로 만든다. 여러 작업이 같이 쓰는 파일이다.

## 작업

### T1 — DB 구조, 권한 규칙, 상태 변경 함수, 자동 삭제
- **목표**
  - spec 3장(권한), 4장(데이터 계약), 5장(상태 규칙), 10장(자동 삭제)을 DB에 구현한다.
  - 대상 테이블: 회차, 소재, 이미 본 게시물 기록, 댓글, 별점, 사람 정보, 허용 목록
- **동작 계약**
  - 모든 테이블에 행 단위 권한 규칙을 건다.
    - 팀원 판정: 로그인한 이메일(소문자)이 현재 DB 허용 목록에 있다(관리자 행 포함). JWT의 팀원 역할 캐시로
      판정하지 않는다. 제거 커밋 이후의 요청은 기존 JWT를 그대로 사용해도 거부한다.
    - 팀원이 아니면 어떤 행도 읽거나 쓸 수 없다.
  - 관리자 행(ardensdevspace@gmail.com, `admin`)은 **마이그레이션이** 허용 목록에 넣는다. seed가 아니라
    마이그레이션이어야 실제 서버에도 들어간다. 이 행은 삭제하거나 역할을 바꿀 수 없다.
  - "나는 팀원인가", "나는 관리자인가" DB 함수를 두고, 규칙과 화면이 이 함수를 같이 쓴다.
  - 소재 상태 변경은 DB 함수 4개(저장, 저장 취소, 삭제, 복구)로만 한다.
    - 각 함수는 `expected_status`와 실제 상태가 같을 때만 원자적으로 변경하고 적용 여부를 돌려준다.
      삭제도 사용자가 본 상태 하나와 비교한다. 허용 상태 둘을 묶은 조건만으로 처리하지 않는다.
    - 팀원이 소재 행을 직접 수정하는 것은 막는다.
  - 소재 생성·본문, 회차·이미 본 기록의 쓰기는 서비스 권한(입구 API)만 가능하다. 팀원의 소재 상태 변경은
    위의 권한 검사된 함수만 허용한다. 메일 반영 함수는 서비스 권한에만 실행을 허용하고, 자동 삭제 함수는
    예약 작업의 DB 역할에만 허용한다. 함수 실행 권한을 명시하고 권한 상승 함수 내부에서도 호출자를 검증한다.
  - 메일 한 통 반영 함수 1개를 둔다(T3가 사용).
    - 입력: 회차 정보와 해석된 카드 목록
    - 한 트랜잭션 안에서 처리한다: `messageId` 중복 확인, 이미 본 게시물 걸러내기, 회차·카드·기록 저장
    - `created`/`duplicate`와 각 수를 돌려준다.
    - 동시 호출에도 회차는 1개다(고유 제약에 기반).
    - 이미 본 기록의 `post_id` 고유 제약과 충돌 처리를 사용한다. 조회 후 삽입만으로 중복을 판정하지 않는다.
      동일 메일 경합은 `duplicate`, 다른 메일의 동일 게시물 경합은 `skipped`로 정상 응답한다.
      여러 게시물 잠금은 일정한 순서로 획득하되 카드 `position`은 메일 순서를 보존한다.
  - 댓글
    - 작성자는 본인으로 강제한다. 수정·삭제는 본인만 할 수 있다.
    - 소재가 `trashed`면 추가·수정·삭제를 거부한다.
    - 본문이 공백뿐이면 거부한다.
    - 수정 시각을 갱신한다.
  - 별점
    - (소재, 사람)당 하나이고 점수는 1~5다. 본인 것만 쓰고 지울 수 있다.
    - 소재가 `trashed`면 거부한다.
  - 사람 정보: 로그인 계정이 생기거나 바뀔 때 DB 트리거가 이메일, 이름, 사진을 채우고 갱신한다(이 작업만 담당).
    팀원이면 누구나 읽을 수 있다.
  - 자동 삭제
    - 매일 도는 예약 작업이다(무료 요금제에서 쓸 수 있는 DB 예약 작업).
    - `trashed_at` 후 30일이 지난 소재와 그 댓글·별점을 지운다. 이미 본 게시물 기록은 남긴다.
    - 30일은 설정값 하나로 둔다.
  - 댓글·별점의 모든 쓰기 경로는 부모 소재 행을 잠그고 현재 상태를 재확인한다. 소재 상태 변경·복구·자동 삭제도
    같은 부모 행 잠금을 사용한다. 권한 검사는 유지하며, 트리거나 RPC를 우회한 직접 쓰기로 규칙을 깨지 못하게 한다.
    자동 삭제의 자식 행 연쇄 삭제는 허용하되 팀원이 휴지통 댓글·별점을 직접 지우는 경로는 막는다.
  - 실시간 신호용 단일 행 테이블(예: `board_revision`, 고정 ID와 증가하는 revision)을 추가한다.
    - 현재 팀원만 SELECT 가능하고 클라이언트 직접 쓰기는 금지한다. 이 테이블의 UPDATE만 구독한다.
    - 회차·소재·댓글·별점·사람 정보·허용 목록의 화면 영향 변경 시 같은 트랜잭션 안에서 revision을 증가시킨다.
      삭제도 이 행의 UPDATE로 알려 준다. 롤백된 변경은 신호를 남기지 않는다.
    - 업무 테이블은 Realtime publication에서 제외한다. 신호 행은 삭제하지 않으며 업무 데이터·행 ID를 담지 않는다.
      삭제 이벤트의 RLS 예외를 피하고, 신호 UPDATE의 RLS는 현재 허용 목록을 조회한다.
    - 작은 팀 규모에 맞춘 재조회 방식이다. 잠금 순서를 일관되게 정하고 신호 행을 잠근 채 업무 행 잠금을
      역순으로 기다리는 경로가 생기지 않도록 한다.
  - 검색용 DB 함수 1개(선택)를 둔다: 검색어와 분류, 상태를 받아 spec 6.5의 조건에 맞는 소재 id를 돌려준다.
    화면 쪽 구현이 편한 방식이면 대체해도 되지만, 댓글 본문도 검색 대상이라는 조건은 지켜야 한다.
- **작업 대상**: `supabase/migrations/*`, `supabase/tests/*`(DB 규칙 테스트), `supabase/seed.sql`(로컬 테스트용
  데이터), 단위 테스트 도구에서 실행하는 DB 동시성·Realtime 통합 테스트 파일(경로는 준비 작업에서 정함)
- **검증**: `supabase start` 후 `supabase test db`가 통과해야 한다. spec 11장의 DB 규칙 항목을 모두 테스트로 확인한다.
  독립 DB 연결이 필요한 동시성·롤백 테스트와 실제 Realtime 클라이언트 권한 테스트는 `pnpm test`에 둔다.
  T1이 DB 수준 경합과 구독 권한을, T3가 API 수준 동시 수신과 응답 계약을 검증한다. 모두 `pnpm verify`에 포함한다.

### T2 — Grok 메일 해석기
- **목표**: 메일 본문 평문을 받아 카드 목록을 돌려주는 순수 함수를 만든다(spec 8.2).
- **동작 계약**
  - 입력: 본문 문자열
  - 출력: 순서가 있는 카드 목록
    - `parsed` 카드: `post_id`, `url`, `category`, `likes`, `retweets`, `summary`, `reason`
    - `raw` 카드: `raw_text`
    - 두 종류 모두 `position`을 가진다.
  - 같은 메일 안의 `post_id` 중복은 여기서 걸러내고 걸러낸 수를 함께 돌려준다. 이미 본 게시물 기록과의 비교는
    T1의 DB 함수가 한다.
  - DB와 네트워크에 접근하지 않는다.
- **작업 대상**: `supabase/functions/_shared/parse.ts`(외부 의존 없는 TypeScript. Deno 서버 기능과 단위 테스트가 함께 불러옴)와 그 테스트 파일
- **검증**: `pnpm test`. spec 11장의 해석기 항목을 모두 테스트로 확인한다.
- **thinking-base**: 양식은 사용자가 Grok에 붙일 문장으로 확정했다(spec 8.1). 해석이 너그러운 방향
  (전각 콜론, 여러 줄 값, 링크 변형)은 Grok이 양식을 조금 어겨도 소재를 놓치지 않기 위해서다. 완전히 어긋난
  부분은 버리지 않고 `raw` 카드로 남긴다(사용자 결정).

### T3 — 메일 받는 입구 API
- **목표**: Supabase 서버 기능 `ingest`를 spec 7장 그대로 만든다.
- **동작 계약**
  - 비밀값을 검사한다. 비교는 시간 차이로 값이 새지 않는 방식으로 한다.
  - 본문을 검증하고 T2 해석기(`supabase/functions/_shared/`)를 호출한다.
  - 요청 처리 로직은 테스트할 수 있게 분리한다. 입력과 DB 호출을 주입받는 함수로 만든다.
  - 서비스 권한으로 T1의 메일 반영 함수를 한 번 호출한다.
  - 응답 키와 값은 spec 7장과 정확히 같아야 한다.
    `created`의 `skipped`는 해석기 내 중복 수와 DB 중복 수를 합산하고, `duplicate`는 세 숫자를 모두 0으로 한다.
  - 로그에 메일 본문 전체를 남기지 않는다.
- **작업 대상**: `supabase/functions/ingest/*`와 테스트
- **검증**: `pnpm test`로 입구 테스트를 돌린다. 로컬 Supabase를 대상으로, 처리 함수를 직접 부르거나 로컬에서 띄운
  서버 기능을 호출한다. 401과 400, 같은 `messageId` 두 번에 회차 1개, 완전 삭제된 게시물이 다시 와도 건너뛰는지를
  확인한다. spec 11장의 동시 메일 수신 두 경우도 API 처리 경로에서 검증하며, 의도적 DB 오류가 성공 응답으로
  바뀌지 않고 이후 재전송이 성공하는지 확인한다.

### T4 — 로그인, 입장 판정, 팀원 관리 화면
- **목표**: spec 3장, 6.6, 6.7
- **동작 계약**
  - 구글 로그인(Supabase Auth, 브라우저에서 처리). 사람 정보는 T1의 DB 트리거가 채운다.
  - 모든 보드 페이지에서 브라우저 쪽에서 입장을 판정한다. 데이터 보호는 DB 규칙이 한다.
    - 비로그인이면 로그인 화면으로 보낸다.
    - 팀원이 아니면 입장 거부 화면으로 보낸다.
    - 공통 권한 확인·캐시 정리 인터페이스를 제공한다. 요청·변경 신호 처리, 연결 복구·탭 복귀, 활성 탭의 30초
      주기 확인에 사용한다. 팀원이 아니라는 판정은 RLS 조회의 빈 결과와 구별해 전용 판정 함수로 확인한다.
    - 거부 시 구독 해제, 보드 캐시 삭제, 진행 중 요청 취소/응답 무효화 후 입장 거부로 이동한다. 확인 중 통신
      오류가 나면 보드 접근을 보류하고 재시도 안내를 보여준다. 제거된 계정으로 임의 단정하지 않는다.
  - 팀원 관리 화면(관리자만): 목록, 추가, 제거(확인 창 포함). 관리자 행은 제거할 수 없다. 오류는 한국어로 안내한다.
  - 공통 레이아웃의 상단 영역을 채운다: 로그인한 사람, 로그아웃, 관리자에게만 보이는 "팀원 관리" 링크.
  - 다른 작업이 쓸 수 있도록 "현재 사람과 관리자 여부"를 알려주는 헬퍼를 내보낸다.
- **작업 대상**: 로그인·콜백·입장 거부·팀원 관리 페이지, 인증 헬퍼(입장 판정 감싸개), 공통 레이아웃의 상단 영역
- **검증**: `pnpm lint && pnpm typecheck && pnpm build`. 권한 자체는 T1의 DB 테스트가 보장한다.

### T5 — 카드의 댓글·별점 영역
- **목표**: spec 6.1의 별점과 댓글 부분을 독립된 화면 조각으로 만든다.
- **동작 계약**
  - 별점
    - 평균(소수 첫째 자리), 인원, 전원의 이름·점수 목록을 보여준다.
    - 내 점수를 주거나 바꾸거나 취소할 수 있다.
    - 별점이 없으면 "아직 별점 없음"을 보여준다.
  - 댓글
    - 오래된 순으로 보여주고, 이름·시각(KST)·"(수정됨)"을 붙인다.
    - 작성할 수 있고, 본인 댓글만 수정·삭제할 수 있다(삭제 확인 창 포함).
  - 읽기 전용 모드(휴지통용)를 지원한다.
  - T6의 공통 데이터 계층이 공급하는 최신 댓글·별점을 표시한다. 카드마다 구독을 만들지 않는다.
    본인의 쓰기 성공 시 공통 재조회 콜백을 호출한다. 필요한 props·콜백 타입은 준비 작업에서 계약을 정한다.
  - DB가 거부하면(예: 그사이 휴지통으로 간 소재) 한국어로 안내한다.
- **작업 대상**: 댓글·별점 화면 조각 파일들. 카드 파일과 페이지 파일은 건드리지 않는다.
- **검증**: `pnpm lint && pnpm typecheck && pnpm build`

### T6 — 소재 모음, 저장됨, 휴지통 페이지와 카드
- **목표**: spec 6.1(카드 틀과 버튼), 6.2, 6.3, 6.4, 6.5, 6.8(소재 상태 실시간)
- **동작 계약**
  - 카드: `parsed`/`raw` 표시, 원본 링크, 반응 수. 각 페이지에 맞는 버튼(삭제 확인 창 포함)을 두고, T5 조각을
    끼운다(휴지통에서는 읽기 전용).
  - 상태 변경은 사용자가 본 `expected_status`를 담아 T1의 DB 함수로 한다. 적용되지 않았다는 응답을 받으면 "다른 팀원이 이미 처리했어요"라고 안내하고
    다시 불러온다.
  - 소재 모음: 회차별 묶음(KST 제목), 빈 회차 숨김, 회차 안에서 메일 속 순서
  - 저장됨: 저장한 시각 최신순과 평균 별점순을 전환한다. 별점 없는 소재는 맨 뒤, 평균이 같으면 저장한 시각
    최신순이다.
  - 휴지통: 휴지통에 들어간 순, 원래 자리 표시, 남은 일수, 복구 버튼
  - 검색과 분류 골라보기(소재 모음·저장됨). 분류 선택지는 `전체/밈/웃긴 게시물/화제/반응/기타/양식 오류`이고,
    검색어는 댓글 본문까지 포함해 찾는다.
  - 페이지 공통 데이터 계층에서 T1의 변경 신호를 한 번 구독하고 T4의 권한 확인을 거쳐 재조회한다.
    댓글·별점 변경도 목록의 검색·정렬과 T5 영역을 함께 갱신한다. 화면에 없는 카드의 변경도 반영한다.
  - 최초 구독 완료 뒤 조회한다. 재조회 중 신호는 후속 조회로 합치고, 이전 검색 조건의 늦은 응답은 무시한다.
    연결 복구·탭 복귀 때도 권한 확인 후 재조회한다. 자동 삭제된 카드와 빈 회차를 정리한다.
  - 반응형: 폰에서 한 줄에 카드 하나
- **작업 대상**: 세 페이지, 카드, 검색·골라보기 조각, 회차 제목 시각 표시 함수
- **검증**: `pnpm lint && pnpm typecheck && pnpm build`. 회차 제목 시각 표시 함수의 단위 테스트(KST, 분 생략
  규칙)를 둔다. spec 11장의 두 계정 화면 확인 항목을 수동 검증하고 결과를 기록한다.

### T7 — Gmail 자동 전달 스크립트와 설정 안내서
- **목표**: spec 9장의 스크립트와, 사용자가 무료 서비스를 직접 연결하는 순서를 담은 안내서를 만든다.
- **동작 계약**
  - 스크립트
    - 한국 시간 오전·오후 각각 한 번 실행하는 함수와 주기 설정 함수. 설치 시 기존 `forwardGrokMail` 트리거를
      지우고 `atHour(8/20).nearMinute(25).everyDays(1).inTimezone('Asia/Seoul')` 두 개를 만든다.
      예상 실행 범위는 8:10~8:40·20:10~20:40이다.
    - 메시지 단위 검색(최초 최근 3일, 이후 영속 저장된 완료 지점부터; 제목의 앞뒤 공백 제거 후
      `강원도 밈 업데이트!`와 정확히 일치). 완료 지점 이전 3일도 겹쳐 검색한다.
      검색으로 찾은 스레드의 각 메시지에서 제목과 수신 시각을 다시 확인한다.
    - 본문의 시작 표시 유무와 무관하게 전달한다. 시작 표시가 없는 메일은 해석기가 원문 카드로 남긴다.
    - 최초 검색 시작점을 호출 전에 저장하고 고정된 시간 구간 단위로 처리한다. 후보 검색을 페이지 끝까지 마치고
      모든 대상이 유효한 `200 created/duplicate`를 받은 경우에만 완료 지점을 전진시킨다.
    - 실행 시간 제한 전에 중단하고 미완료 구간부터 재개한다. 실패가 있으면 해당 구간을 유지하며 로그로 알린다.
      재개할 때 현재 기준 최근 3일로 축소하지 않는다. 성공 ID 캐시는 제한된 크기로 유지하며 서버 멱등성을 따른다.
    - LockService로 겹치는 실행을 막고 잠금을 못 얻으면 다음 주기에 맡긴다. 검색·API 오류·강제 중단 이후에도
      완료 지점이 미처리 구간을 넘어가지 않아야 한다.
    - 설정값은 스크립트 속성에서 읽는다.
  - 안내서(`docs/setup.md` 또는 README, 한국어)
    - Supabase 프로젝트 만들기, 마이그레이션 적용(관리자 행 포함), 구글 로그인 설정(구글 클라우드 OAuth 클라이언트
      → Supabase, 사이트 주소를 로그인 후 돌아올 주소로 등록)
    - 서버 기능 `ingest` 배포, `INGEST_SECRET` 설정, 입구 주소 확인
    - Cloudflare 정적 사이트 배포와 내 도메인 연결, 사이트 환경 변수 목록
    - 스크립트 설치, 속성 입력, 주기 설정, 권한 승인
    - 완료 지점의 의미, 3일 넘는 중단 후 자동 따라잡기, 반복 실패 로그 확인과 원인 해결 후 재실행 절차
      (완료 지점을 임의로 현재 시각으로 바꾸지 않음), 원본 영구 삭제 시 복구 불가
    - Grok 요청 끝에 붙일 문장(spec 8.1 그대로)
    - 확인 방법: 오전·오후 실행 후 해당 메일이 보드에 뜨는지, 메일·스크립트 실행 시각을 비교한다.
    - 주의: 무료 DB는 일주일간 활동이 없으면 잠든다. 매일 오는 메일이 활동이 되지만, 메일이 멈추면 깨워야 한다.
- **작업 대상**: `gmail-script/Code.gs`(+ 스크립트 설정 파일), `docs/setup.md`
- **검증**: 스크립트는 자동 테스트 범위 밖이다(사용자가 정한 자동 검사 범위). 사람 확인 증거는 배포 후 실제 메일
  1통이 회차로 나타나는 것이다. 이번 실행에서는 코드 리뷰로 spec 9장과 맞는지 확인한다. 제목이 일치하고 시작
  표시가 없는 메일도 전달되는지, 같은 스레드의 제목 불일치·조회 구간 밖 메시지는 제외되는지 확인한다.
  배포 후 수동 검증에는 4일 이상 중단한 완료 지점에서의 재개, API 실패 뒤 재실행, API 성공 직후 저장 전 중단에
  따른 중복 재전송, 검색 페이지 중간 중단과 겹치는 실행을 포함한다. 실제로 4일을 기다릴 필요는 없으며 테스트용
  스크립트 설정과 메일로 확인한다. 운영 완료 지점을 건너뛰거나 초기화하지 않는다.

## 공유 파일 안내

- 공통 레이아웃 파일: 준비 작업이 만들고 상단 영역은 T4만 채운다. T6은 페이지 안쪽만 담당하고 레이아웃의 페이지
  이동 링크는 준비 작업의 틀을 쓴다.
- `package.json`: 작업 중에 의존성 추가가 필요하면 각자 추가해도 되지만, 스크립트 항목은 준비 작업이 정한 것을
  바꾸지 않는다.
- DB 구조와 타입: T1만 마이그레이션을 쓴다. 화면 쪽 작업은 T1이 끝난 뒤의 구조를 따른다.
- 준비 작업에서 T5의 데이터 props·쓰기 성공 콜백 계약을 정의한다. T5는 이를 사용하고, T6가 공통 데이터 계층을
  구현해 연결한다. T4는 권한 판정·거부 처리를 소유하고 T6는 그 인터페이스를 호출한다.

## 흐름 (사람이 읽는 설명)

1단계에서는 DB(T1), 해석기(T2), Gmail 스크립트와 안내서(T7)를 서로 독립적으로 병렬 진행한다. T7은 spec의
API 계약만 따르면 된다. 2단계에서는 T1과 T2에 기대는 입구 API(T3), T1에 기대는 로그인·팀원 관리(T4), 댓글·별점
조각(T5)을 병렬로 진행한다. 3단계에서 로그인 헬퍼(T4)와 댓글·별점 조각(T5)을 쓰는 페이지와 카드(T6)를 만든다.

## 구현 시 참고한 공식 문서

- [Supabase Postgres Changes](https://supabase.com/docs/guides/realtime/postgres-changes): DELETE 이벤트의 RLS
  제약 때문에 업무 테이블 대신 권한 검사되는 변경 신호 UPDATE를 사용한다.
- [PostgreSQL 행 잠금](https://www.postgresql.org/docs/current/explicit-locking.html): 부모 소재 잠금과 일관된
  잠금 순서로 상태 변경·댓글·별점 경합을 처리한다.
- [Apps Script LockService](https://developers.google.com/apps-script/reference/lock/lock-service): 예약 실행이
  겹쳐 완료 지점을 잘못 갱신하지 않도록 스크립트 잠금을 사용한다.
